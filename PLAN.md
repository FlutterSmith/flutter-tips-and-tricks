# Flutter Tips: Rebuild Plan

> Status: **DRAFT for approval**. Nothing gets built until you sign off.
> Source analysed: `FlutterSmith/flutter-tips-and-tricks`, a GitHub fork of `bizz84/flutter-tips-and-tricks` (Andrea Bizzotto, "Code with Andrea").
> Snapshot date: 2026-09-26. Current stable toolchain at time of writing: Flutter 3.47.x / Dart 3.13.x, Riverpod 3.x.

---

## 0. TL;DR

The original is a **read-on-GitHub archive of 163 social-media tips** (Twitter/LinkedIn, 2021–2024). The tips are good, but the repo is a pile of screenshots. Code is trapped in images, nothing compiles or gets tested, there's no search or categories, the metadata is hand-maintained (and has copy-paste bugs), and it's been abandoned since June 2024, so a good chunk is now stale (Riverpod 2 APIs, cancelled Dart macros, Xcode 15 workarounds).

We'll build a **content-as-code handbook**:

- Every tip is Markdown with typed frontmatter (category, tags, level, verified Flutter/Dart versions, origin).
- Every code snippet is **text, excerpted from real Dart files that CI analyzes and tests** against current stable Flutter. Snippets can't silently rot.
- UI screenshots are **generated by golden tests**, so they're reproducible and never go stale unnoticed.
- A small **Dart CLI** (`tips`) validates content, scaffolds new tips, syncs excerpts, and generates the README catalog and prev/next nav.
- A fast, searchable **docs site** (Astro Starlight → GitHub Pages) with categories, tags, learning paths, dark mode, OG images and RSS. The repo still reads well on GitHub.
- Content is **triaged** (all 164 upstream folders): 89 keep, 44 modernize, 13 rewrite, 10 merge, 8 retire, giving **146 tips** plus new originals. Every adapted tip carries attribution, as the MIT license requires.

## 1. Understanding the original

### 1.1 The idea

Andrea Bizzotto posted short, visual Flutter/Dart tips on Twitter and LinkedIn roughly weekly from mid-2021 to mid-2024. Social posts are ephemeral and hard to search, so this repo is the **permanent archive**. It also works as a funnel to his articles and courses on codewithandrea.com and to a closed-source companion app (fluttertips.dev).

### 1.2 Who it's for

Beginner-to-intermediate Flutter developers who want quick, practical, "did you know?" knowledge: widgets, Dart language features, Riverpod, testing, VSCode/DevTools tooling, Firebase, and app architecture. The whole thing leans toward his stack (Riverpod + Firebase + feature-first architecture).

### 1.3 How it works end to end

```
 Idea ─► design code screenshot (carbon-style PNG/GIF) ─► post on X + LinkedIn
                                                            │
                                                            ▼
                         create tips/NNNN-slug/ ── index.md (text + ![](NNNN.png))
                                                ├─ NNNN.png / .gif / .mp4
                                                └─ main.dart (sometimes: raw snippet dump)
                                                            │
             hand-edit previous tip's "Next" link ◄─────────┤
             hand-add row to 42 KB README table  ◄──────────┘
                    (ID | title | tweet | LinkedIn | article)
                                                            │
                                                            ▼
                                     GitHub renders Markdown ─► reader
```

- **No build, no tooling, no CI.** The only script, `optimize-pngs.sh`, runs `optipng` on the current folder and needs Homebrew.
- Metadata (tweet/LinkedIn/article URLs) lives in the README table. For 23 tips it's also in HTML comments like `<!-- TWITTER|url -->`, which looks like the input to an unpublished app/site importer. 18 tips still carry `<!-- TODO:UPDATE -->`.

### 1.4 Why it's built this way

- **Image-first** because the tips were designed for social feeds, where a pretty code screenshot beats a text block. The repo just re-hosts those assets.
- **Plain Markdown on GitHub** means zero infra and zero maintenance for a solo creator, and it makes use of GitHub's discoverability (stars).
- **Numbered folders and a flat table** mirror the order of the posting schedule, not any learning structure.

These were sensible choices for a social-first creator. They're the wrong choices for a **reference you can learn from, search, copy from, and trust**, and that's the gap we fill.

**How the new repo complies:**

1. `LICENSE` (MIT) lists both holders: `Copyright (c) 2022 Andrea Bizzotto` (for adapted material) and `Copyright (c) 2026 <you>`.
2. `ATTRIBUTION.md` explains the upstream origin and links `bizz84/flutter-tips-and-tricks`, with a generated table of every adapted tip → its upstream path.
3. Each adapted tip has `origin:` frontmatter, and the site renders "Adapted from Flutter Tips & Tricks by Andrea Bizzotto (MIT)" with a link.
4. No upstream branding assets are copied. A validation rule fails CI if a file hash matches one of those three banners.
5. Everything we add is MIT too. One license for the whole repo keeps it simple and matches upstream.

*(This is a plain-language reading of MIT, which is about as permissive as licenses get. The main care points are the notice and the branding.)*

## 4. Vision & principles

**Product:** *"The Flutter tips handbook that's actually maintained: searchable, copy-pasteable, tested against today's Flutter."*

1. **Text over pixels.** Code is always text. Images only show *results* (UI, DevTools).
2. **Every snippet compiles.** If it's Dart, CI analyzes it. If it has behavior, CI tests it.
3. **Every tip states its truth window**: `verified_with: flutter 3.47`, plus `status: current | outdated | archived`.
4. **Generated, not hand-maintained**: catalog, nav, tag pages, attribution table.
5. **Great on GitHub *and* on the web.**
6. **Accessible by default**: alt text is required, contrast-checked themes, captions for video.
7. **Small and fast**: per-asset size budgets, repo < 40 MB.
8. **Easy to contribute**: `tips new`, templates, one command to validate locally.

## 5. Architecture

### 5.1 Repository layout

```
<repo>/
├─ content/
│  └─ tips/
│     └─ <slug>/                    # e.g. stopwatch-measure-time
│        ├─ index.md                # frontmatter + prose + excerpt markers
│        └─ assets/                 # generated goldens, DevTools screenshots, webm/mp4
├─ examples/                        # Flutter package: the single source of truth for code
│  ├─ pubspec.yaml
│  ├─ analysis_options.yaml         # strict (flutter_lints + extra rules)
│  ├─ lib/tips/<slug>/*.dart        # real code with `// #docregion name` markers
│  ├─ test/tips/<slug>_test.dart    # behavior tests
│  └─ test/goldens/<slug>_test.dart # screenshot generators (tag: golden)
├─ tool/                            # Dart CLI package `tips_cli`
│  ├─ bin/tips.dart
│  ├─ lib/src/{model,validate,excerpt,generate,scaffold,media}/…
│  └─ test/…                        # unit tests for the tooling
├─ site/                            # Astro + Starlight website
│  ├─ astro.config.mjs
│  └─ src/…                         # theme, tag/category pages, OG images
├─ pubspec.yaml                     # Dart pub workspace: [tool, examples]
├─ README.md                        # hero + generated catalog (between markers)
├─ CATALOG.md                       # generated: all tips by number/category/tag
├─ ATTRIBUTION.md                   # generated upstream table + license notes
├─ CONTRIBUTING.md · CODE_OF_CONDUCT.md · LICENSE · CHANGELOG.md
└─ .github/
   ├─ workflows/{ci.yml, site.yml, freshness.yml, links.yml}
   ├─ ISSUE_TEMPLATE/{tip-idea.yml, bug-in-tip.yml, outdated-tip.yml}
   └─ pull_request_template.md
```

### 5.2 Tip format (frontmatter schema)

```yaml
---
id: 57                         # stable public number (new sequence, never reused)
slug: stopwatch-measure-time   # folder name = URL
title: Measure execution time with Stopwatch
summary: DateTime.now() isn't monotonic. Use Stopwatch for timing code.
category: dart                 # one of the fixed categories (5.3)
tags: [performance, async]
level: beginner                # beginner | intermediate | advanced
published: 2026-10-12
updated: 2026-10-12
verified_with: { flutter: "3.47", dart: "3.13" }
packages: { http: "^1.2.0" }   # optional; drives "requires" badge
status: current                # current | outdated | archived
origin:                        # present only on adapted tips
  upstream_id: 116
  upstream_path: tips/0116-measure-time/index.md
  change: modernized           # kept | modernized | rewritten | merged
related: [future-wait-records, debouncing-timer]
dartpad: true                  # optional: generate "Open in DartPad" (pure-Dart tips)
---
```

The body uses excerpt markers that the tool fills in:

````md
<?code-excerpt "stopwatch-measure-time/measure.dart" region="helper"?>
```dart
// (auto-synced from examples/lib/tips/stopwatch-measure-time/measure.dart)
```
````

Rules:

- A Dart fence without a marker **fails** validation, unless its info string says `dart nocheck` and a reason comment follows. That's for intentionally broken "❌ don't do this" code, which can also live in `examples/` with `// ignore:` directives.
- Shell/YAML/JSON snippets may be inline (not compiled), but they're still linted for fence language.

### 5.3 Taxonomy

Fixed categories (sidebar groups): **Dart language · Widgets & Layout · State management · Architecture · Testing · Tooling & IDE · DevTools & Performance · Firebase & Backend · Platform & Release · Practices**.
Tags are free-form but validated against `content/tags.yaml`, so there are no typos or near-duplicates.
**Learning paths** (`content/paths/*.yaml`) are ordered tip lists, e.g. "Riverpod from zero", "Testing Flutter apps", "Modern Dart 3".

### 5.4 Build pipeline

```
                ┌──────────────────────────── tips CLI (Dart) ─────────────────────────────┐
 examples/*.dart│  excerpt sync ──► content/tips/*/index.md  (code blocks filled from source) │
                │  validate     ──► schema · ids · slugs · tags · alt text · asset budgets    │
 goldens (test) │               ──► orphan assets · dead internal links · fence rules         │
   ──► assets/  │  generate     ──► README catalog · CATALOG.md · ATTRIBUTION.md              │
                │               ──► tips.json (public data feed) · prev/next nav metadata      │
                └───────────────────────────────┬────────────────────────────────────────────┘
                                                ▼
                    site/ (Astro Starlight) reads content/ + tips.json
                    ─► static HTML + Pagefind search + OG images + RSS
                                                ▼
                                    GitHub Pages (custom domain optional)
```

### 5.5 `tips` CLI (Dart, in `tool/`)

| Command | Purpose |
|---|---|
| `tips new "<title>" --category x` | Scaffold `content/tips/<slug>/index.md` + `examples/lib/tips/<slug>/` + test stub, assign next ID |
| `tips sync [--check]` | Fill/verify code excerpts from `examples/`. `--check` fails if stale (CI). |
| `tips validate` | All content rules (5.2, 5.6). Human-readable errors with file:line. |
| `tips generate [--check]` | README/CATALOG/ATTRIBUTION/tips.json. `--check` fails on diff (CI). |
| `tips media` | Convert GIF → WebM/MP4 + poster PNG (ffmpeg), optimize PNG (oxipng), enforce budgets |
| `tips import-upstream <path>` | One-off migrator (Phase 2), tested against fixtures |

Built with `args`, `yaml`, `path`, `checked_yaml`/`json_serializable` for the typed model, `test` for tests. The model classes are immutable, and validation is a list of small `Rule` objects (Strategy pattern), so rules are unit-testable and easy to extend.

### 5.6 Validation rules (initial set)

Unique `id` and `slug` · slug == folder · category ∈ enum · tags ∈ tags.yaml · `summary` ≤ 160 chars · every image has alt text (≥ 5 words for non-decorative) · every asset referenced and every reference exists · PNG ≤ 300 KB, video ≤ 2 MB, no GIF > 500 KB (convert) · no upstream branding hashes · `origin` required when content derives from upstream · `verified_with.flutter` within 2 minor versions of the CI toolchain, otherwise a warning plus an auto `outdated` badge · internal links resolve · external links checked weekly (not per-PR, to avoid flakes).

### 5.7 `examples/` package

- A single Flutter package (simpler dependency graph than 150 packages) with all tip deps (riverpod, go_router, fpdart, rxdart, etc.), pinned by `pubspec.lock` in git.
- Firebase tips: code is **analyzed only**, using fakes where behavior matters (no live Firebase in CI).
- Goldens: generated on Linux CI only with bundled fonts, so they're deterministic. They're tagged `golden` so contributors on macOS aren't blocked. Candidate library: `alchemist`, falling back to plain `matchesGoldenFile` + font loader if it's unmaintained at build time.
- `dart format` + `flutter analyze --fatal-infos` + `flutter test` in CI.

### 5.8 Website (`site/`)

**Astro + Starlight**, chosen for built-in Pagefind full-text search, dark mode, an accessible theme, sidebar groups, "Edit this page", i18n-ready structure, and excellent Lighthouse scores. It's zero-JS by default.
Extras: a category landing page with cards · tag pages · learning-path pages · per-tip badges (level, verified version, status, "Adapted from…") · copy button on code · "Open in DartPad" for pure-Dart tips · OG image per tip (generated at build) · RSS/Atom feed · `tips.json` public feed.
Content wiring: a Starlight content collection with a glob loader pointed at `../content/tips`, plus a schema mirrored from the Dart model. If the loader can't reach outside `site/` cleanly, a prebuild step copies the files instead.
Deploy: GitHub Actions → GitHub Pages on push to `main`. Preview builds on PRs as artifacts.

*Alternative considered:* **Jaspr** (Dart static site) would keep the stack all-Dart, but it has a less mature search/theme ecosystem. **Docusaurus** is heavier React and slower. Starlight gives the most polish for the least custom code.

### 5.9 CI workflows

| Workflow | Trigger | Steps |
|---|---|---|
| `ci.yml` | PR + push | Flutter stable (pinned via `.fvmrc`/action input) → `dart pub get` (workspace) → `tips validate` → `tips sync --check` → `tips generate --check` → `dart format --set-exit-if-changed` → `flutter analyze` → `flutter test --exclude-tags golden` → goldens on Linux → `tool` tests → site build |
| `site.yml` | push to `main` | build + deploy Pages |
| `freshness.yml` | weekly cron | run the same pipeline against **latest** Flutter stable; on failure open/update a single "Toolchain drift" issue listing affected tips |
| `links.yml` | weekly cron | `lychee` on content + site; opens an issue on failure |

Plus: Dependabot (actions, pub, npm), CODEOWNERS, branch protection guidance in CONTRIBUTING.

## 6. Content strategy & migration

### 6.1 Principles

- **Triage every upstream tip** (Appendix A): **Keep** (light edit, code → text, alt text), **Modernize** (APIs changed), **Rewrite** (advice is wrong or obsolete but the topic is valuable), **Merge** (fold into another tip), **Retire** (obsolete, opinion/time-bound, or low value).
- **New numbering** (1…N in publication order of *our* repo), with the upstream ID kept in `origin.upstream_id`. The site redirects `/upstream/<n>` → new slug for people arriving from old references.
- **House style:** open with the problem in one sentence, then the snippet, then *why*, then pitfalls, then related links. ≤ 350 words. Social-media cruft ("Found this useful? share the original tweet 🙏") is removed.
- **Our own additions:** the plan reserves slots for new tips covering 2025–26 Flutter (e.g. `Column(spacing:)`, `AppLifecycleListener`, Riverpod 3 mutations/offline, `package:web` + Wasm, `dart fix` data-driven fixes, sealed-class `Result`, `Stopwatch`). Those fill the gaps the retirements leave.

### 6.2 Migration pipeline

```
upstream tips/NNNN-*/index.md
   │ tips import-upstream (automated, idempotent, fixture-tested)
   ▼
content/tips/<slug>/index.md  ← frontmatter pre-filled (id, title, origin, guessed category)
   status: draft, prose copied, social footer & nav stripped,
   every image flagged "TODO alt" and "TODO code-as-text"
   │ manual/assisted curation per tip (triage action)
   ▼
examples/lib/tips/<slug>/*.dart + tests + goldens → excerpt markers → alt text → status: current
```

Drafts are excluded from the site and README until promoted, so partial migration never ships half-done pages.

## 8. Quality gates

### 8.1 Definition of Done per tip
- [ ] Frontmatter valid; category/tags/level set; `verified_with` = CI toolchain
- [ ] All Dart shown is excerpted from `examples/` (or explicitly `nocheck` with reason)
- [ ] Behavior covered by a test where there's behavior to test
- [ ] UI tips: screenshot generated by a golden test
- [ ] Every image has meaningful alt text; videos have a poster + text description
- [ ] `origin` set if adapted; advice re-checked against current docs
- [ ] ≤ 350 words, house style, at least one `related` link

### 8.2 Launch checklist
Fresh clone → `dart pub get && dart run tips validate` works on macOS/Linux/Windows · site works with JS disabled (except search) · keyboard-only navigation · no image > budget · repo < 40 MB · README renders well on GitHub mobile · every link 200 · attribution visible on site footer + ATTRIBUTION.md.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| **Scale**: ~150 tips × (code + test + alt text) is a lot of work | Automated importer; batch by category; drafts hidden; ship v0.x with complete categories rather than all at once |
| Package API churn (Riverpod, go_router) | `pubspec.lock` pinned; weekly `freshness.yml` flags drift early; `verified_with` + auto `outdated` badge |
| Golden flakiness across OSes | Generate/compare on Linux CI only with bundled fonts; tag-excluded locally |
| Node toolchain in a Dart-centric repo | Isolated in `site/`; contributors editing tips never need Node (CI builds the site) |
| Upstream-derived content seen as "just a fork" | Substantial rewrite, new structure, tested code, our own design and additions, with clear, generous attribution |
| Firebase tips can't run in CI | Analyze-only + fakes; documented in the tip |
| Scope creep (app, i18n) | App is optional Phase 5; i18n is structurally possible but out of scope for v1 |

Need to know how long an async call takes? Wrap it in a generic helper built on `Stopwatch`:

<?code-excerpt "stopwatch-measure-time/measure.dart" region="helper"?>
```dart
Future<(T, Duration)> measure<T>(Future<T> Function() action) async {
  final stopwatch = Stopwatch()..start();
  final result = await action();
  return (result, stopwatch.elapsed);
}
```

**Why not `DateTime.now()`?** Wall-clock time can jump (NTP sync, DST, the user changing the clock), so the difference can be wrong or even negative. `Stopwatch` uses a monotonic clock.
